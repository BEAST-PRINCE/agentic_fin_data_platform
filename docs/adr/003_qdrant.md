# ADR 003: Using Qdrant for the Vector Database

**Status:** Accepted  
**Date:** July 2026  

## 📜 Context and Problem Statement
While DuckDB handles structured aggregations (numbers and dates), the AI Agents needed a way to search through the unstructured text of financial news articles based on *meaning* rather than exact keyword matches. This requires converting text to vector embeddings and storing them in a dedicated Vector Database.

The market for Vector Databases has exploded, and I needed one that was lightweight enough to run locally in Docker, but powerful enough to handle JSON payload filtering (which is critical to prevent LLM hallucination).

## 🤔 Considered Options
1. **ChromaDB:** Very popular in the LangChain ecosystem. Easy to use, but historically struggled with complex payload filtering and performance at scale compared to Rust-based alternatives.
2. **Pinecone / Weaviate Cloud:** Excellent enterprise solutions, but they require internet connectivity and paid API credits. This violates the "Local-First" architecture requirement.
3. **pgvector (PostgreSQL Extension):** Would allow me to keep vectors and tabular data in one database. However, I had already rejected Postgres in favor of DuckDB (ADR 001), so adding it just for vectors defeated the purpose.
4. **Qdrant:** Written in Rust. Extremely fast. Runs perfectly in a local Docker container. Exceptional support for Payload Filtering.

## ✅ Decision
I chose **Qdrant** as the primary vector storage and retrieval engine.

It is deployed via `docker-compose.yml`. During the `vector_indexer.py` job, the 384-dimensional embeddings generated by Sentence Transformers are upserted into Qdrant alongside a strict JSON payload containing the article's title, domain, date, and KeyBERT tags.

When the Researcher Agent queries Qdrant, it uses cosine similarity to find the nearest vectors, and immediately returns the attached JSON payload to the LLM context window.

## 📈 Consequences
* **Positive:** Sub-millisecond vector search latency due to Qdrant's Rust architecture.
* **Positive:** The web dashboard (port 6333) is fantastic for debugging and verifying that embeddings actually made it into the collection.
* **Positive:** Payload filtering allows the agents to run semantic searches constrained by hard dates (e.g., "Find news about EV batteries, but only vectors where `publish_date` > '2026-07-01'").
* **Negative:** It is a separate infrastructure component that must be maintained and monitored, rather than having a single unified database.
